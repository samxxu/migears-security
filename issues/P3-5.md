# P3-5 — Csrf::validate() throws the same csrfValidationFailed() exception for …

## Finding / 问题

- EN: Csrf::validate() throws the same csrfValidationFailed() exception for both "no stored token" and "token mismatch", giving no signal to distinguish an attack attempt from a missing session.
- 中文: Csrf::validate() 对「无存储令牌」和「令牌不匹配」两种情况抛出相同的 csrfValidationFailed() 异常，无法区分攻击尝试与会话缺失。
- Where / 位置: `src/Csrf.php:78-84`
- Verification / 验证: static / 仅静态推断

- 2026-10-01 · `owner — migears-security` · `rejected` — the uniform rejection is deliberate, and the
  signal the item asks for is not lost. Both throws share one factory with a single fixed message
  (`src/Exception/SecurityException.php:42-45`), and separating them would tell the remote party whether
  a session/token exists at all — the information-disclosure case OWASP's CSRF guidance answers
  uniformly. The distinction is available where it can be acted on: `Csrf` is storage-agnostic by design
  (`README.md:105-138`, `README.md:418-448`) and the caller injects the `$getter`, so the caller already
  knows whether its own store holds a token. Probe through the module's own autoloader
  (`/tmp/migears-security-probe/p3-5.php`): both paths throw
  `MiGears\Security\Exception\SecurityException` with the identical message
  `CSRF token validation failed.`, while a caller-side check on its own store returns
  `no-session-token` vs `token-present` — so an application can log or alert on the difference without
  putting it on the wire in an exception. No README claim says the two are distinguished, so there is
  nothing to keep in sync. Re-graded: this does not sit on the P0–P3 defect ladder at all — the current
  behaviour is the safer side.
