# P3-6 — Password::verify() does not reject or handle passwords longer than the …

## Finding / 问题

- EN: Password::verify() does not reject or handle passwords longer than the bcrypt 72-byte limit — it passes them directly to password_verify(), which silently truncates on the verify side. If a hash was created by another system with a long password, verify() would silently truncate and potentially match a wrong prefix.
- 中文: Password::verify() 未拒绝或处理超过 bcrypt 72 字节限制的密码——直接传给 password_verify()，后者在验证端静默截断。如果哈希由其他系统用长密码创建，verify() 会静默截断并可能匹配错误前缀。
- Where / 位置: `src/Password.php:73-76`
- Verification / 验证: static / 仅静态推断

  but the fix forks on behaviour and that pick is not mine. Probe through the module's own autoloader
  (`/tmp/migears-security-probe/p3-6.php`): two 76-byte passwords sharing a 72-byte prefix
  (`p1 = 'a'x72 . 'AAAA'`, `p2 = 'a'x72 . 'ZZZZ'`, `p1 !== p2`) both make `Password::verify()` return
  `true` against a bcrypt hash of `p1` — so a *wrong* password verifies — while `Password::hash(p1)`
  throws `SecurityException: Password exceeds the 72-byte limit of the selected hashing algorithm.`
  (`src/Password.php:56-58`). A 73-byte hash verifies a 72-byte-plus-different-tail input just the same.
  So the two halves are asymmetric today: a credential `hash()` refuses can still be *verified*
  (`src/Password.php:73-76`).
  **The decision needed:** should `verify()` mirror `hash()` and reject input past bcrypt's 72 bytes —
  and if so, throw (`SecurityException::passwordTooLong`, symmetric with `hash()`) or return `false`
  (a verifier that does not throw)? Either is a behaviour change on a public method, and it carries a
  second consequence I will not resolve silently: a bcrypt hash produced elsewhere from a >72-byte
  password would then stop verifying entirely, and this module's own `needsRehash()` → `hash()` upgrade
  path could not repair it, because `hash()` throws on exactly that input.
  **The other end of the fork** is to keep `verify()` a pass-through to `password_verify()` and state the
  asymmetry in both README halves (the paragraph at `README.md:71-74` / `README.md:383-385` already
  explains the `hash()` side but says nothing about `verify()`). No code changed pending the ruling.
